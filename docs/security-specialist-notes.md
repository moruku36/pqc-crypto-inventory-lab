# 情報処理安全確保支援士：暗号棚卸しから考える

本ノートは実装と基礎概念を結び付ける学習補助です。特定年度の出題予測ではありません。
「何を守るか」「誰のどの鍵か」「どの検証まで行ったか」を答案で区別します。

## 操作から知識につなげる読み方

最初は16テーマを一度に覚えず、[操作ガイド](getting-started.md)で確認した結果から読み進めます。

| 操作で見たこと | 次に読むテーマ | 自分の言葉で説明してみること |
|---|---|---|
| RSAとAESの両方が登場した | 公開鍵暗号・共通鍵暗号・ハイブリッド暗号 | 通信でそれぞれ何を担当するか |
| 証明書の公開鍵と署名が別の項目だった | PKI・X.509・電子署名 | 証明書の誰の鍵と、誰の署名を見ているか |
| SHA-1がUNKNOWNだが見直し対象だった | ハッシュ | 判定名だけでなく用途を確認する理由 |
| TLS 1.3の鍵交換がUNKNOWNだった | TLS・鍵交換 | 暗号スイート名だけで分かる範囲 |
| RSAの移行候補が複数書かれていた | 暗号アルゴリズム移行・PQC | 署名と鍵確立で移行候補が違う理由 |
| スコアに運用のUNKNOWNがあった | Crypto Agility | ファイル調査だけでは分からない運用を何で確認するか |

### 例：RSA証明書を見たら、どう説明するか

「RSAを使っている」という一文だけでは、何に使っているかが曖昧です。
今回の結果なら、「証明書に含まれる公開鍵の方式はRSAだった」と観測範囲を限定します。
そこから、通信本文をRSAで暗号化しているとも、RSAで鍵交換したとも断定できません。
このように、観測した項目と、そこから言えることの範囲を合わせる練習に使えます。

以下はテーマ別の説明です。各項目の「今回の実装」を入口にすると、操作結果と結び付けられます。

## 公開鍵暗号

- **試験ポイント**：公開鍵と秘密鍵の組を使う。暗号化、署名、鍵共有で役割を区別する。
- **今回の実装**：`tls_scanner.public_key_info`で証明書の公開鍵方式を識別する。
- **実務**：相手認証、署名検証、共通鍵の確立を支える。
- **間違えやすい点**：公開鍵は公開可能だが、対応する秘密鍵の管理は必須。方式名だけでは用途が分からない。

## 共通鍵暗号

- **試験ポイント**：共有する秘密鍵で暗号処理を行う。鍵配送・モード・nonce管理が重要。
- **今回の実装**：設定のAES、TLSスイートのAES-256を評価する。
- **実務**：通信本文・保存データなど大量データの保護。
- **間違えやすい点**：AES採用だけでは完全性を保証しない。SAFEラベルはモードや実装の保証ではない。

## ハイブリッド暗号

- **試験ポイント**：公開鍵方式で共通鍵を確立し、本文を共通鍵方式で保護する構成を説明する。
- **今回の実装**：証明書の公開鍵、鍵交換、共通鍵暗号を別項目として出す。
- **実務**：安全な通信・データ共有で役割を分担する。
- **間違えやすい点**：「古典方式＋PQC」のハイブリッドとは文脈が異なる。両者とも組合せ方の安全性が必要。

## RSA

- **試験ポイント**：素因数分解の困難性と関連し、署名と暗号化では別の方式・パディングを使う。
- **今回の実装**：RSA公開鍵と証明書署名を量子脆弱として分類する。
- **実務**：既存PKI、署名、過去の鍵配送方式の棚卸し。
- **間違えやすい点**：RSA証明書だからRSAで鍵交換したとは限らない。鍵長増加だけでPQCにはならない。

## ECC

- **試験ポイント**：楕円曲線上の離散対数問題に基づく方式群。ECDSAは署名、ECDHは鍵共有。
- **今回の実装**：EC公開鍵の符号化だけでは用途を断定せずECCと表示する。
- **実務**：署名、TLS鍵共有、SSHなど。
- **間違えやすい点**：短い鍵長は低い安全性を直ちに意味しない。一方、古典的ECCはPQCではない。

## PKI

- **試験ポイント**：CA、信頼の起点、証明書チェーン、発行・更新・失効の関係を説明する。
- **今回の実装**：標準sslの信頼ストアを使って接続時の証明書検証を行う。
- **実務**：公開鍵と主体の結び付けを第三者の署名で検証する。
- **間違えやすい点**：署名が数学的に正しくても、信頼しないCAや対象名不一致なら受け入れられない。

## X.509

- **試験ポイント**：主体公開鍵情報、発行者、署名方式、有効期間、拡張の役割を区別する。
- **今回の実装**：`certificate_info`で公開鍵と証明書署名OID、有効期限を取得する。
- **実務**：サーバ証明書、クライアント証明書、コード署名証明書等。
- **間違えやすい点**：証明書へのCAの署名方式と、証明書に格納された主体の公開鍵方式は別情報。

## TLS

- **試験ポイント**：認証・鍵確立・通信内容の保護を段階と役割に分けて説明する。
- **今回の実装**：通常のハンドシェイクを1回行い、選択されたバージョンとスイートを取得する。
- **実務**：Web/APIなどの盗聴・改ざん対策と接続先認証。
- **間違えやすい点**：TLS 1.3のスイート名だけでは鍵交換方式を決定できない。1回の観測は全対応方式の一覧ではない。

## 電子署名

- **試験ポイント**：秘密鍵で署名し公開鍵で検証する。改ざん検知と署名者の確認に使う。
- **今回の実装**：証明書署名のOIDを解析し、RSA/ECDSA等の量子リスクを記録する。
- **実務**：証明書、コード配布、文書承認。
- **間違えやすい点**：署名だけでは内容を秘匿できない。否認防止には鍵管理や本人確認の運用も関わる。

## ハッシュ

- **試験ポイント**：原像、第二原像、衝突の困難性を区別する。暗号化のような復号操作はない。
- **今回の実装**：hashlib等のSHA呼び出しをASTで検出し、SHA-1用途の確認を優先する。
- **実務**：完全性検査、署名の構成要素、鍵導出等。
- **間違えやすい点**：単なるハッシュには送信者認証がない。パスワード保存には専用のKDF等が必要。

## 鍵交換・鍵確立

- **試験ポイント**：鍵共有と認証は別の機能。中間者対策と一時鍵の役割を説明する。
- **今回の実装**：TLS 1.2ではスイートに明示されたECDHE/DHEファミリーのみ取得する。
- **実務**：通信ごとの共有秘密から通信鍵を導出する。
- **間違えやすい点**：PFSは古典的な長期鍵漏えい対策で、量子計算に対する保証ではない。KEMは署名ではない。

## 証明書

- **試験ポイント**：対象名、信頼チェーン、有効期間、用途、失効など複数条件を確認する。
- **今回の実装**：TLS接続では標準の検証を有効にするが、ローカル証明書の構造解析は信頼検証ではない。
- **実務**：更新忘れによる停止の防止、発行と配布の管理。
- **間違えやすい点**：有効期限内であることと、失効していないことは同義ではない。

## CRL / OCSP

- **試験ポイント**：CRLは失効リスト、OCSPは証明書状態の照会。更新時刻や応答検証も必要。
- **今回の実装**：CRL/OCSP確認は未実装で、TLS出力とレポートに限界を明示する。
- **実務**：秘密鍵漏えいや誤発行時の失効状態確認。
- **間違えやすい点**：OCSPのgoodだけで証明書の全検証が終わるわけではない。到達不能時の扱いも設計が必要。

## 暗号アルゴリズム移行

- **試験ポイント**：資産と用途の把握、依存関係、互換性、段階移行と切戻しを具体化する。
- **今回の実装**：`report.replacement`は用途に応じた候補を示し、一対一置換を断定しない。
- **実務**：鍵・証明書・クライアント・プロトコルをまたぐ移行計画。
- **間違えやすい点**：規格の存在と、自社のライブラリ/PKIで利用できることは別。草案を確定義務として扱わない。

## Crypto Agility

- **試験ポイント**：暗号変更時に安全性・運用・相互接続を維持できる能力を考える。
- **今回の実装**：`scoring.py`が10項目を評価し、静的根拠、申告、UNKNOWNを区別する。
- **実務**：更新可能なAPI、鍵管理、証明書運用、交渉、互換性試験の整備。
- **間違えやすい点**：設定可能なら安全とは限らない。許可方式の制限とダウングレード対策が必要。

## PQC

- **試験ポイント**：量子計算による攻撃を想定した公開鍵方式。量子鍵配送とは異なる。
- **今回の実装**：RSA/ECC等の棚卸しと、ML-KEM・ML-DSA・SLH-DSAの用途別候補を提示する。
- **実務**：長期間秘匿するデータの鍵確立、長期署名、更新可能なPKIの検討。
- **間違えやすい点**：ML-KEMは共有秘密の確立、ML-DSA/SLH-DSAは署名。PQC採用だけで実装全体が安全にはならない。

## 記述練習

1. RSA証明書を観測しても、TLSの鍵交換方式を断定できない理由を説明する。
2. UNKNOWNの項目について、追加で必要な証拠を「対象・取得方法・判断基準」で列挙する。
3. SHA-1の利用を見つけた際、用途確認から移行検証までの手順を60〜100字で書く。
4. 署名をML-KEMへ置換する提案の誤りを、提供する機能の違いから説明する。
